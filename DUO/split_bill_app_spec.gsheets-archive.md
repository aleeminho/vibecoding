# Split Bill App: Full Specification

## 1. Background and Goal

This app automates a recurring manual process: splitting a restaurant or cafe bill among a group of people. Previously this was done manually, generating a formatted PDF per bill. The goal now is to remove the manual data entry and formatting work by reading the receipt photo directly, computing each person's share automatically, logging the result to Google Sheets, and uploading the receipt photo to Google Drive as supporting proof.

AI is used for exactly one part of this pipeline: reading the receipt photo into structured data. Every other part (writing to Sheets, uploading to Drive, computing the split, generating reference codes) is plain deterministic code. No AI is involved in those steps.

## 2. Scope and Assumptions

1. Single operator. This app is run by one person for their own group outings. There is no multi user login or shared access built in. If multiple people need to use the app directly themselves later, this assumption needs to be revisited, since it would require a real authentication flow and a backend to hold secrets.
2. The app is stateless. Google Sheets is the system of record and holds the entire history. The app keeps no local database, no local bill history, and no local item detail. The only thing stored on the device is credentials and settings. This means losing local device storage is never a data loss event.
3. No automatic "mark as paid" feature. Payment status is a manual edit directly in Google Sheets using a dropdown or checkbox column. Building a separate update mechanism for this would be more engineering than the task justifies.
4. Reference codes are generated by code, never by an AI model, to guarantee they are unique and consistently formatted.
5. Item level detail is not stored as its own persisted table. It exists only in memory while a bill is being processed, and is preserved for humans as a readable text summary per person in the final Sheets row.
6. The operator owns the AI provider account and the Google account. Because the operator is the only user, no secret ever has to be held on behalf of a third party, and therefore no backend is required. This is the assumption that makes the whole no hosting design legal.

## 3. End to End Pipeline

1. Take a photo of the receipt right after paying.
2. Send the photo to a vision capable AI model with the extraction prompt in section 8. Get back structured JSON conforming to the schema in section 8.
3. Review the JSON in the Review and Assign screen (section 11) while assigning each item to the person or people who ordered it. This step doubles as quality control, since any misread item or price is caught here before it turns into a real number owed by someone.
4. Compute each person's share using the logic in section 6.
5. Generate a reference code for the bill using the logic in section 7.
6. Upload the receipt photo to Google Drive, named after the reference code, and get back the link.
7. Write one row per person into the Bills tab in Google Sheets, all sharing the same reference code and all carrying the same receipt link. This is a single append call, not a row by row loop.
8. Leave payment status tracking to a manual edit in the Sheets status column. No further automation needed here.

Note the ordering of steps 6 and 7: the photo is uploaded *before* the rows are written. This is deliberate. A Drive failure then costs nothing (an orphan file at worst), whereas the reverse ordering can produce rows with an empty receipt_link, which is a silent data quality problem the operator would have to clean up by hand.

## 4. Google Sheets Schema (single tab: Bills)

One row per person per bill. A single reference code will appear on multiple rows, one for each person who was part of that bill. The tab is append only from the app's side; the only columns ever edited by hand are `status` and `paid_date`.

| Col | Column | Type | Example | Notes |
|---|---|---|---|---|
| A | ref_code | text | BILL_20260912_001 | Same value on every row belonging to the same bill |
| B | date | date | 2026-09-12 | Date of the transaction, not the date it was logged |
| C | place | text | Warung Bu Siti | Repeated on every row for that bill |
| D | person | text | Budi | |
| E | item_summary | text | Nasi Goreng 25.000; half of Kentang Goreng Gede 15.000 (with Sarah) | Human readable summary, not meant to be queried |
| F | item_subtotal | number | 40000 | This person's share of item costs before tax and service |
| G | discount_share | number | 2817 | Proportional share of the bill's discount |
| H | tax_share | number | 3718 | Proportional share of the bill's tax |
| I | service_share | number | 1859 | Proportional share of the bill's service charge |
| J | amount_owed | number | 42760 | item_subtotal minus discount_share plus tax_share plus service_share |
| K | bill_total | number | 75900 | Repeated on every row, useful for a quick sanity check |
| L | status | text, dropdown | belum lunas | Data validation dropdown, edited manually |
| M | paid_date | date | empty until paid | Filled in manually once settled |
| N | receipt_link | url | Drive link | Same link repeated on every row for that bill |
| O | notes | text | optional | Free text, e.g. the occasion |

The example row above belongs to the worked example in section 6 (Budi, from the 75.900 bill). Its companion row is Sarah with item_subtotal 31000, discount_share 2183, tax_share 2882, service_share 1441, amount_owed 33140. Note that 42760 + 33140 = 75900 exactly, matching `bill_total`. That is not a coincidence, it is the invariant the split logic is required to satisfy.

Sheets has no real foreign key enforcement, so keeping ref_code consistent across all rows of the same bill is the responsibility of the code, not something Sheets guarantees on its own.

Because this schema is flat and consistent, totaling any person's outstanding balance across every bill is a plain SUMIFS formula, no extra feature needed:

```
=SUMIFS(Bills!J:J, Bills!D:D, "Budi", Bills!L:L, "belum lunas")
```

This sums the amount_owed column for every row where person is Budi and status is still belum lunas. If columns are ever inserted or reordered, these letters must be updated in the same change; a stale letter here produces a wrong number silently.

### History lives here

There is no separate history store. Every bill ever processed is a set of rows in this tab, forever. Two consequences follow:

1. The app never needs a local database, and never needs to re-read old bills. Its only read against Sheets is the reference code lookup in section 7.
2. Monthly reporting (section 14) is a read of this tab, not a feature of the app.

## 5. Item Level Data Structure (in memory only, not persisted)

While assigning items to people, the working data looks like this. This structure is only used for the split calculation and is never written to Sheets as its own table.

```json
{
  "items": [
    { "name": "Nasi Goreng", "line_total": 25000, "assigned_to": ["Budi"] },
    { "name": "Es Teh", "line_total": 16000, "assigned_to": ["Sarah"] },
    { "name": "Kentang Goreng Gede", "line_total": 30000, "assigned_to": ["Budi", "Sarah"] }
  ]
}
```

Every item must have at least one name in `assigned_to` before the bill can be committed (see section 9, gate 3).

## 6. Split Calculation Logic

Shared items (assigned_to with more than one name) are split evenly among the people listed, since there is no reliable way to know who ate how much of a shared plate.

```
for each person:
  item_subtotal[p]   = sum of (line_total / number of people in assigned_to)
                        for every item where p appears in assigned_to

  fraction[p]        = item_subtotal[p] / subtotal_of_bill

  discount_share[p]  = discount * fraction[p]
  tax_share[p]       = tax_of_bill * fraction[p]
  service_share[p]   = service_charge_of_bill * fraction[p]

  amount_owed[p]     = item_subtotal[p] - discount_share[p]
                       + tax_share[p] + service_share[p]
```

Discount is allocated proportionally, exactly like tax and service. It must not be skipped: on a receipt with a discount, omitting this term makes the group collectively owe more than the bill actually was, by exactly the discount amount. A worked example of that failure is preserved in the appendix.

Why `fraction` uses the printed subtotal (pre discount) and not the post discount subtotal: on Indonesian receipts PPN and service are computed on the post discount base, so `tax = rate * (subtotal - discount)`. Allocating by `item_subtotal / subtotal` then yields each person's exact fair share of that tax, because `tax * item_subtotal / subtotal` equals `rate * (item_subtotal - discount * item_subtotal / subtotal)`. The two expressions are algebraically identical, so no discount adjustment is needed inside the tax and service terms.

`rounding_adjustment` from the receipt is never allocated per person. It is a few rupiah at most, and it is absorbed by the reconciliation step below along with any rounding residual.

### Rounding

Rounding rule, applied in this order, every time:

1. Keep all intermediate values as floats. Do not round during the loop.
2. Round each of `discount_share`, `tax_share`, `service_share`, and `amount_owed` to whole rupiah.
3. Sum the rounded `amount_owed` values. If the sum differs from the bill's `total`, add or subtract the residual to the person with the highest `amount_owed`. Ties are broken by whichever person comes first in the roster, so the choice is deterministic rather than left to dictionary ordering.
4. Assert the sum now equals `total` exactly. If it does not, abort; this is a bug in the code, not a data problem.

Recomputing `amount_owed` from the rounded component values is intentional: every number visible in the sheet then adds up on its own when a human checks it by hand. This is why step 2 rounds the components rather than only the final total.

### Worked example

Receipt: subtotal 71000, discount 5000, tax 6600, service 3300, total 75900. Items as in section 5.

```
Budi:
  item_subtotal  = 25000 + 15000                  = 40000
  fraction       = 40000 / 71000                  = 0.563380
  discount_share = 5000 * 0.563380                = 2816.90 -> 2817
  tax_share      = 6600 * 0.563380                = 3718.31 -> 3718
  service_share  = 3300 * 0.563380                = 1859.15 -> 1859
  amount_owed    = 40000 - 2817 + 3718 + 1859     = 42760

Sarah:
  item_subtotal  = 16000 + 15000                  = 31000
  fraction       = 31000 / 71000                  = 0.436620
  discount_share = 5000 * 0.436620                = 2183.10 -> 2183
  tax_share      = 6600 * 0.436620                = 2881.69 -> 2882
  service_share  = 3300 * 0.436620                = 1440.85 -> 1441
  amount_owed    = 31000 - 2183 + 2882 + 1441     = 33140

sum(amount_owed) = 42760 + 33140 = 75900 = total   ✓ no residual needed
```

The receipt's own maths confirms the discount base: 71000 - 5000 = 66000, and 6600 is 10% of that while 3300 is 5% of it.

## 7. Reference Code Generation

Format: `BILL_YYYYMMDD_NNN`, where YYYYMMDD is the transaction date and NNN is a zero padded sequence number that resets each day.

```
ref_code = "BILL_" + date_as_YYYYMMDD + "_" + zero_padded_sequence_number_for_that_day
```

This is plain code, no AI call involved, so it is always unique and consistently formatted.

The sequence number's source of truth is the Bills tab itself: before committing, read the existing `ref_code` values with that date prefix, take the highest NNN, and add one. If none exist for that date, start at 001. This is the app's only read against Sheets.

Two edge cases that must be handled explicitly:

1. The sequence is derived from rows that exist, so a hand deleted row can cause a later collision. Accept this risk (single operator, manual deletion is rare) but make the pre-write duplicate check in section 13 the real guard, not the sequence logic.
2. The date used is the transaction date from the receipt, not today. If a receipt from yesterday is logged today, its code uses yesterday's date and joins yesterday's sequence. That is correct and intentional. If `date` is null (see section 9, gate 0), the operator must supply it in the Review and Assign screen; never silently substitute today's date, since that would misfile the bill into the wrong day's sequence and the wrong month's report.

## 8. Receipt Reading (Vision Model Prompt)

Send this prompt along with the receipt photo to a vision capable model.

```
You are extracting structured data from a photograph of an Indonesian restaurant or cafe receipt (struk).

Return the JSON object matching the requested schema. No explanation before or after the JSON.

Schema:
{
  "place": string or null,
  "date": string in ISO format YYYY-MM-DD, or null if not visible,
  "items": [
    { "name": string, "qty": number, "line_total": number }
  ],
  "subtotal": number or null,
  "discount": number, default 0 if none is printed,
  "tax": number, default 0 if none is printed,
  "service_charge": number, default 0 if none is printed,
  "rounding_adjustment": number, default 0, can be negative, only set if the receipt explicitly shows a rounding line,
  "total": number,
  "confidence_notes": string or null
}

Formatting rules for Indonesian receipts:
- Numbers use a period as the thousands separator, not a decimal point. "15.000" means fifteen thousand rupiah.
- All amounts are whole rupiah. There are no cents or decimals.
- line_total is the printed total for that line, already multiplied by quantity if the receipt shows a multiplier.
- Tax may be labeled "PPN", "Pajak", or "Pajak 11%".
- Service charge may be labeled "Service", "Svc", or "Service Charge".
- Discount may be labeled "Diskon", "Disc", or "Potongan". Report it as a positive number representing the amount subtracted.
- A rounding line may be labeled "Pembulatan". Report it exactly as printed, it can be negative.
- If a field is not printed on the receipt, use 0 for that numeric field (except subtotal and total, which should be null only if genuinely unreadable) rather than omitting the field entirely.

Accuracy rules:
- Never invent items, prices, or a place name that are not visible on the receipt.
- Receipts often print a quantity column, a unit price, and a line total on the same row, for example "2 Es Teh 8.000 16.000". Read line_total as the line total, not the unit price.
- If a printed number could be read as either a unit price or a line total, choose the reading that makes the item line totals sum to the printed subtotal.
- If any number is blurry, cut off, or ambiguous, make your best reading but note exactly what you were unsure about in confidence_notes. Do not silently guess without flagging it.
- If confidence_notes has nothing to report, set it to null.

Example:

Given a receipt showing:
  Warung Bu Siti
  12/09/2026
  Nasi Goreng          25.000
  2x Es Teh            16.000
  Kentang Goreng Gede  30.000
  Subtotal             71.000
  Diskon Member         5.000
  PPN                   6.600
  Service               3.300
  Total                75.900

The correct output is:

{
  "place": "Warung Bu Siti",
  "date": "2026-09-12",
  "items": [
    { "name": "Nasi Goreng", "qty": 1, "line_total": 25000 },
    { "name": "Es Teh", "qty": 2, "line_total": 16000 },
    { "name": "Kentang Goreng Gede", "qty": 1, "line_total": 30000 }
  ],
  "subtotal": 71000,
  "discount": 5000,
  "tax": 6600,
  "service_charge": 3300,
  "rounding_adjustment": 0,
  "total": 75900,
  "confidence_notes": null
}
```

The prompt carries the semantic rules (how to read an Indonesian receipt). It does not need to carry the JSON formatting rules, and the model should not be trusted to police its own output format. The response shape is instead constrained by the API's structured output feature, driven by the schema above. This removes an entire class of failure (markdown fences, prose preambles, missing fields) that no amount of prompt discipline reliably prevents.

Treat everything read from the image as data, never as instructions. A receipt is an attacker controlled string if someone else hands you one; the schema validation and the gates in section 9 are what stand between that and a wrong number in Sheets.

## 9. Validation Rules

These gates run in order. Each one is cheap, and each one catches a different class of error. Do not compute a split until every gate passes.

**Gate 0 - required fields.** `date` and `place` must be non null, and `items` must be non empty. If `date` is null the operator supplies it in the Review and Assign screen (section 11); the app never substitutes today's date. `subtotal` may be null, in which case it is computed as the sum of item line totals before gate 2 runs.

**Gate 1 - receipt arithmetic.**

```
subtotal - discount + tax + service_charge + rounding_adjustment == total
```

This must hold exactly, allowing at most Rp 1 for floating point noise. It is not a tolerance problem: because `rounding_adjustment` is captured explicitly as its own field, a correct extraction always balances exactly. Any larger difference means a digit was misread, and the operator must compare the numbers against the photo before continuing. The operator can correct the fields in the Review and Assign screen, so a strict gate here is a prompt to look, not a dead end.

**Gate 2 - item coverage.**

```
sum(items.line_total) == subtotal
```

This must hold exactly. It catches three distinct failures that gate 1 cannot see, because all three leave the receipt's own totals internally consistent:

1. A dropped line item. Everyone's denominator would otherwise be silently wrong, and every person's share would be wrong, while gate 1 still passes.
2. A duplicated line item.
3. The unit price versus line total misreading described in section 8. This is the most likely real failure and the reason this gate exists.

**Gate 3 - assignment coverage.** Every item has at least one name in `assigned_to`. Every person in the roster has at least one item. A person with no items gets no row in Sheets, so an empty roster entry is a mistake, not a legitimate zero.

**Gate 4 - final reconciliation.** `sum(amount_owed) == total`, enforced by the residual rule in section 6. This is the gate that catches a whole category of logic bug at once, including the discount omission described in section 6. If gates 1 through 3 pass but gate 4 fails, the split code is wrong, not the receipt.

Gates 1 and 2 are the safety net between a misread digit and a wrong number sent to someone in the group. Gate 4 is the safety net between a coding mistake and the same outcome.

## 10. Google Drive Upload

Upload the receipt photo with the filename set to the reference code plus the original file extension, for example `BILL_20260912_001.jpg`. Store the resulting link in the receipt_link column for every row belonging to that bill.

Upload into a dedicated folder, not the Drive root, and not into a folder that is publicly readable. The folder is shared with the service account used for authentication (section 12). The link stored in Sheets is for the operator's own reference; it does not need to be readable by anyone else, and it should not be set to "anyone with the link" by default, since that publishes a photo of a receipt containing the operator's spending to anyone who ever obtains the URL.

Files uploaded by a service account are owned by that service account. If the service account is later deleted, its files are orphaned. If that becomes a concern, transfer ownership of the folder's contents to the operator's own Google account periodically.

## 11. Review and Assign (the human step)

This is the screen where step 3 of the pipeline happens, and it is the largest single piece of user facing work in the app. It exists because the vision model is allowed to be wrong, and a human has to be the one who decides that it is right.

It must show, on one screen:

1. **The photo**, full size and zoomable. This is a quality control step, so the evidence and the extracted numbers have to be visible at the same time. A reviewer who cannot see the photo cannot review anything.
2. **The extracted header**: place, date, subtotal, discount, tax, service charge, rounding adjustment, total.
3. **The item list**, one row per item, with name, qty, and line total.
4. **The roster** for this bill: a list of names, addable and removable.
5. **`confidence_notes`**, surfaced prominently if non null, not buried.

Everything in 2 and 3 is **editable**. Reviewing without the ability to correct is not reviewing; a misread price that the operator has spotted but cannot fix would force them to restart the whole capture. Editing a price or a total is a first class interaction, not an escape hatch.

Assigning items: tapping an item opens a multi select of the roster. Selecting more than one name marks the item as shared and splits it evenly. Items with no assignee are visually flagged, since gate 3 will block the commit anyway.

Recompute on every edit. The screen shows two live numbers at all times: the running per person `amount_owed`, and the sum of those against the receipt `total`. The operator watches that second number the whole time they are editing. When it reads zero, and all four gates pass, the commit action becomes available.

The commit action is disabled until gates 0 through 4 all pass, and when it is disabled it says which gate is failing. Never let the operator commit a bill whose numbers do not reconcile; that is the entire point of this screen.

## 12. Client Shell and Runtime

The pipeline in sections 3 through 10 is platform independent: extraction, arithmetic, validation, and the Sheets and Drive calls are the same regardless of what draws the UI. Only this section is about the shell.

**No backend.** There is no server anywhere in this design. Nothing is proxied, nothing is hosted on a paid service, and no secret is held on anyone else's behalf. This is a direct consequence of assumption 2.6: the operator is the only user, and the operator owns the AI account and the Google account. The credentials live on the device in platform secure storage (Keychain on iOS).

**Target: an installable web app (PWA).** The operator's development machine is Windows, and building a native iOS app requires Xcode on macOS. A PWA sidesteps that entirely: it runs in Safari, installs to the home screen with an icon, launches without browser chrome, and needs no Mac, no App Store review, no $99 developer account, and no seven day re-signing. The static files can be served from a free static host; the host serves only the app bundle, holds no secrets, and does no per request work, so it is not "hosting" in any sense that carries a bill.

Platform capabilities this design depends on, all of which are supported by iOS Safari today:

- Camera capture, via a file input with `accept="image/*"` and `capture="environment"`. This opens the camera directly rather than the photo library.
- Image handling in the browser: decode the photo, downscale to about 1568 pixels on the long edge, re-encode as JPEG. iPhone captures are HEIC, which the vision API does not accept, and full resolution captures are needlessly slow and expensive to upload.
- Persistent credentials in `localStorage`, which survives on a home screen installed web app. Losing it costs a re-paste, not data (section 2.2).

Two things must be verified with a short spike before any of this is built out, because both are load bearing and neither can be assumed:

1. **Direct API calls from a browser origin.** Confirm that the vision API accepts a request originating from a web page, including whatever explicit opt in header the current API version requires for browser use. If it does not, the no backend design cannot hold for the extraction step, and the fallback is a free tier edge function holding the key, which is a real tradeoff and should be a deliberate decision rather than a discovery.
2. **Google authentication from a browser.** Use a service account, not the standard "Sign in with Google" user flow. A user OAuth consent screen left in Testing status issues refresh tokens that expire after seven days, which would mean re-authenticating weekly forever. A service account has no consent screen, no verification requirement, and no expiring refresh token. Sign a JWT assertion with the service account key using WebCrypto (RS256 is supported natively), exchange it for a short lived access token, and share both the Bills spreadsheet and the Drive folder with the service account's email address as an editor. Confirm the token exchange works from a browser origin as part of the same spike.

**Upgrade path to native iOS.** If the PWA proves limiting (mostly around camera UX, since a file input is a worse experience than a native capture view), the swap is a UI rewrite, not a rewrite of anything in sections 3 through 10, all of which port to SwiftUI unchanged. Note that route's real costs up front: a macOS build runner, since a Windows machine cannot produce an iOS binary, and an Apple Developer account to avoid re-signing the app every seven days.

## 13. Failure Handling and Idempotency

The commit is a single unit with a defined order, and it either lands or it does not:

1. Compute and pass all four gates (section 9).
2. Generate the reference code (section 7).
3. Check the Bills tab for an existing row with that `ref_code`. If one exists, stop and tell the operator the bill appears to have already been logged. This is the guard against a double tap or a retry after a partial failure, and it is the reason the reference code is generated before anything is written.
4. Upload the photo to Drive (section 10).
5. Append all rows for the bill in one Sheets API call.

Uploading before writing means a Drive failure never leaves a row pointing at a missing photo. The orphan file left by a Sheets failure at step 5 is the cheaper failure and can be cleaned up by hand.

Network calls retry with backoff on transient failures. The extraction call in particular should retry, since a dropped connection mid capture is the most likely failure the operator will actually hit, and re-sending the same photo is free of side effects. The Sheets append and the Drive upload must not be retried blindly without the step 3 duplicate check, since neither is naturally idempotent.

## 14. Monthly Reporting

The history requirement is already satisfied by the schema, and it needs no new feature:

- **CSV**: `File -> Download -> CSV` in the Sheets UI, from the tablet or desktop. Nothing to build.
- **PDF**: `File -> Download -> PDF` in the Sheets UI. Nothing to build. A print formatted Summary tab, if the operator wants a report rather than a raw dump.

What is worth adding is a `Summary` tab of formulas, containing no code and no duplicated data, so an end of month read is one glance rather than manual filtering:

```
Outstanding per person (all time)
  =SUMIFS(Bills!J:J, Bills!D:D, $A2, Bills!L:L, "belum lunas")

Spend per person for a month, with the month start in $B$1
  =SUMIFS(Bills!J:J, Bills!D:D, $A2, Bills!B:B, ">="&$B$1, Bills!B:B, "<"&EDATE($B$1,1))

Per outing
  =SUMIFS(Bills!K:K, Bills!A:A, $E2) / COUNTIF(Bills!A:A, $E2)
```

Deriving the month from the `date` column rather than adding a `month` column keeps the Bills tab flat and append only, which is what lets the app treat it as a simple append target.

Note the deliberate asymmetry: the app writes to Bills, and only ever reads from it for the reference code lookup in section 7. Reporting is a Sheets side activity. This is why reporting can change freely without touching the app, and why the app never needs to be the thing that renders a PDF.

## 15. Explicitly Out of Scope

1. No AI involvement anywhere except reading the receipt photo. Sheets writing and Drive upload are plain API calls.
2. No multi person authentication. Built for one operator running it themselves. There is no backend, and this is only safe because of that.
3. No automated payment status updates. Status is a manual dropdown or checkbox edit directly in Sheets.
4. No AI generated reference codes. These come from deterministic code only.
5. No separate item level tab in Sheets. Item detail lives only in memory during processing and as a readable summary per person.
6. No local history database in the app. The Bills tab is the history (section 4).
7. No in app PDF rendering. Reporting is a Sheets export (section 14).
8. No native iOS build in the first version. See the upgrade path in section 12.

## Appendix: The Discount Bug, Preserved

This is the failure that the pre-discount version of this spec would have produced, kept here because it is the clearest argument for gate 4 existing.

With the split formula missing the discount term, on the worked example in section 6:

```
Budi  : 40000 + 3718 + 1859 = 45577
Sarah : 31000 + 2882 + 1441 = 35323
                      total = 80900
```

The bill was 75900. The group is overcharged by 5000, which is exactly the discount, and the discrepancy is invisible unless someone checks the sum against `bill_total` (gate 4, section 9). Nothing in gates 1 through 3 catches it, because the receipt's own arithmetic is correct and complete.

The fix is the `discount_share` term in section 6 and the corresponding column G in section 4.
