# Split Bill App: Full Specification

## 1. Background and Goal

This app automates a recurring manual process: splitting a restaurant or cafe bill among a group of people. Previously this was done manually, generating a formatted PDF per bill. The goal now is to remove the manual data entry and formatting work by reading the receipt photo directly, computing each person's share automatically, logging the result, and storing the receipt photo as supporting proof.

AI is used for exactly one part of this pipeline: reading the receipt photo into structured data. Every other part (persisting the bill, storing the photo, computing the split, generating reference codes) is plain deterministic code. No AI is involved in those steps.

This replaces an earlier design that used Google Sheets and Google Drive as the persistence layer. That design was abandoned because the Google integration cost (service accounts, JWT assertion signing, folder sharing, OAuth token handling, and two unverified assumptions about browser origins) was disproportionate to the problem. See the archived spec for that version. The core logic in sections 5 through 9 and section 11 carried over from it unchanged, which is a useful signal that the core was right and only the plumbing was wrong.

## 2. Scope and Assumptions

1. Single operator. This app is run by one person for their own group outings. Participants are free text names belonging to one operator's account, not user accounts of their own. Section 4 leaves a seam for changing this later, but nothing in this spec should be built assuming it.
2. There is one hosted dependency: Supabase. It provides the database, the photo storage, and the operator's login. The target is the free tier, so the running cost is zero, but the design is no longer literally serverless and should stop being described that way.
3. The app is a thin client over Supabase. It holds no local database and no local bill history. It caches nothing that cannot be re-fetched. The only durable local state is the session token.
4. No automatic "mark as paid" feature. Payment status is a manual toggle in the app.
5. Reference codes are generated by code, never by an AI model, to guarantee they are unique and consistently formatted.
6. Receipt photos are stored privately. There is no public URL for a receipt, ever. Access is through short-lived signed URLs.
7. The model provider's API key never reaches the client. It lives as a secret on a Supabase Edge Function (section 12). The provider is currently DeepSeek, and the parts that depend on that choice are confined to section 8 and the request block in the Edge Function.

## 3. End to End Pipeline

1. Get the receipt photo in, either by taking it right after paying or by picking an earlier one from the photo library. Both paths matter: an input with `capture="environment"` opens the camera directly and cannot reach the library at all, so the library needs its own input rather than being a setting on the same one.
2. The photo is uploaded to a Supabase Edge Function, which calls a vision capable model with the prompt in section 8 and returns structured JSON conforming to the schema there.
3. Review the JSON in the Review and Assign screen (section 11) while assigning each item to the person or people who ordered it. This step doubles as quality control, since any misread item or price is caught here before it turns into a real number owed by someone.
4. Compute each person's share using the logic in section 6.
5. Validate against the four gates in section 9. Do not proceed until all four pass.
6. Generate a reference code for the bill using the logic in section 7.
7. Upload the receipt photo to Supabase Storage.
8. Commit the whole bill, items, assignees, and per person amounts in a single database transaction (section 13).
9. Marking a bill paid is a manual toggle in the app, which sets `status` and `paid_date`. This is one UPDATE and needs no automation.

Step 8 is a single transaction, which is a meaningful improvement over the design this replaces. Either the bill, all of its items, all of its assignees, and all of its per person amounts land together, or nothing does. There is no partial state to clean up and no ordering trick needed to avoid orphaned rows.

## 4. Data Model

Postgres via Supabase. Money is stored as `integer` rupiah, never as a float or a numeric with decimals, since rupiah has no minor unit in practice. All the rounding decisions in section 6 therefore happen in application code and are frozen into integers at commit time.

```sql
create table bills (
  id                  uuid primary key default gen_random_uuid(),
  owner_id            uuid not null default auth.uid() references auth.users (id),
  ref_code            text not null unique,
  place               text not null,
  bill_date           date not null,
  subtotal            integer not null check (subtotal >= 0),
  discount            integer not null default 0 check (discount >= 0),
  tax                 integer not null default 0 check (tax >= 0),
  service_charge      integer not null default 0 check (service_charge >= 0),
  rounding_adjustment integer not null default 0,
  total               integer not null check (total >= 0),
  receipt_path        text,
  notes               text,
  extraction          jsonb,
  created_at          timestamptz not null default now()
);

create table bill_participants (
  id             uuid primary key default gen_random_uuid(),
  bill_id        uuid not null references bills (id) on delete cascade,
  person         text not null,
  user_id        uuid references auth.users (id),
  item_subtotal  integer not null,
  discount_share integer not null,
  tax_share      integer not null,
  service_share  integer not null,
  amount_owed    integer not null,
  status         text not null default 'belum lunas'
                   check (status in ('belum lunas', 'lunas')),
  paid_date      date,
  unique (bill_id, person)
);

create table bill_items (
  id         uuid primary key default gen_random_uuid(),
  bill_id    uuid not null references bills (id) on delete cascade,
  position   integer not null,
  name       text not null,
  qty        integer not null default 1,
  line_total integer not null,
  unique (bill_id, position)
);

create table bill_item_assignees (
  item_id        uuid not null references bill_items (id) on delete cascade,
  participant_id uuid not null references bill_participants (id) on delete cascade,
  primary key (item_id, participant_id)
);
```

Notes on the model:

- `bills.id` is the real identity of a bill. `ref_code` is a human readable handle the operator can say out loud, and it is still unique, so a `unique` constraint on it is the real duplicate guard (section 13).
- `owner_id` on `bills` is the hinge for the row level security policies in section 12. Every other table reaches the owner through its parent bill, so policies on the child tables are `exists` subqueries rather than their own column.
- `user_id` on `bill_participants` is nullable and unused in version one. It is the seam that makes "participants can log in and see their own balance" a small change rather than a redesign.
- `extraction` keeps the raw model output alongside the validated numbers. When a number looks wrong three weeks later, this is the only way to tell whether the model misread the receipt or the operator mistyped the correction. It costs a few kilobytes.
- `receipt_path` is a Storage object path, not a URL. URLs are signed on demand and expire, so storing one would store a broken link.

Two views carry the reporting in section 14:

```sql
create view v_outstanding as
  select person, sum(amount_owed) as outstanding, count(*) as bills
  from bill_participants
  where status = 'belum lunas'
  group by person;

create view v_monthly_spend as
  select date_trunc('month', b.bill_date) as month,
         p.person,
         sum(p.amount_owed) as total
  from bill_participants p
  join bills b on b.id = p.bill_id
  group by 1, 2;
```

The invariant `sum(amount_owed) == total` for a bill cannot be expressed as a plain Postgres check constraint, because it spans rows that are inserted in the same statement. It is enforced in application code (gate 4, section 9) and made visible by this view, which flags any bill where the two disagree:

```sql
create view v_bill_imbalance as
  select b.id, b.ref_code, b.total,
         sum(p.amount_owed) as participants_total,
         b.total - sum(p.amount_owed) as difference
  from bills b
  join bill_participants p on p.bill_id = b.id
  group by b.id
  having b.total <> sum(p.amount_owed);
```

This view should return zero rows. If it ever returns a row, there is a bug in the split code, and the row tells you exactly which bill. Adding a deferred constraint trigger to make this a hard database level guarantee is possible and is left as optional hardening rather than a requirement.

## 5. Item Level Data Structure

Items are now persisted (they were memory-only in the design this replaces, where the persistence layer made storing them awkward). The reason to persist them is not analytics: it is that a month later, when somebody questions their share, "here is the line item breakdown of what you ordered" is a different kind of answer than "trust the total". It also makes a bad split re-computable instead of a manual redo.

In memory, while assigning, the working shape is:

```json
{
  "items": [
    { "name": "Nasi Goreng", "qty": 1, "line_total": 25000, "assigned_to": ["Budi"] },
    { "name": "Es Teh", "qty": 2, "line_total": 16000, "assigned_to": ["Sarah"] },
    { "name": "Kentang Goreng Gede", "qty": 1, "line_total": 30000, "assigned_to": ["Budi", "Sarah"] }
  ]
}
```

At commit time this is written as rows across `bill_items` and `bill_item_assignees`. Every item must have at least one assignee before the bill can be committed (gate 3, section 9).

The per person readable summary that the old design stored as a text column is now rendered from the items wherever it is displayed, not stored. The format stays the same: items in receipt order, each rendered as `name` plus the person's share of that line, with shared lines marked. For example:

```
Nasi Goreng 25.000; half of Kentang Goreng Gede 15.000 (with Sarah)
```

Two properties worth preserving, because they make the string self-checking for a human: the numbers listed sum to that person's `item_subtotal`, and a shared line shows the person's own share, not the full line total.

## 6. Split Calculation Logic

Shared items (assigned_to with more than one name) are split evenly among the people listed, since there is no reliable way to know who ate how much of a shared plate.

```
for each person:
  item_subtotal[p]   = sum of (line_total / number of people in assigned_to)
                        for every item where p appears in assigned_to

  fraction[p]        = item_subtotal[p] / subtotal_of_bill

  discount_share[p]  = discount * fraction[p]
  tax_share[p]       = tax_of_bill * fraction[p]
  service_share[p]   = service_charge_of_bill * fraction[p]

  amount_owed[p]     = item_subtotal[p] - discount_share[p]
                       + tax_share[p] + service_share[p]
```

Discount is allocated proportionally, exactly like tax and service. It must not be skipped: on a receipt with a discount, omitting this term makes the group collectively owe more than the bill actually was, by exactly the discount amount. A worked example of that failure is preserved in the appendix.

Why `fraction` uses the printed subtotal (pre discount) and not the post discount subtotal: on Indonesian receipts PPN and service are computed on the post discount base, so `tax = rate * (subtotal - discount)`. Allocating by `item_subtotal / subtotal` then yields each person's exact fair share of that tax, because `tax * item_subtotal / subtotal` equals `rate * (item_subtotal - discount * item_subtotal / subtotal)`. The two expressions are algebraically identical, so no discount adjustment is needed inside the tax and service terms.

`rounding_adjustment` from the receipt is never allocated per person. It is a few rupiah at most, and it is absorbed by the reconciliation step below along with any rounding residual.

### Rounding

Rounding rule, applied in this order, every time:

1. Keep all intermediate values as floats. Do not round during the loop.
2. Round each of `discount_share`, `tax_share`, `service_share`, and `amount_owed` to whole rupiah.
3. Sum the rounded `amount_owed` values. If the sum differs from the bill's `total`, add or subtract the residual to the person with the highest `amount_owed`. Ties are broken by whichever person comes first in the roster, so the choice is deterministic rather than left to hash ordering.
4. Assert the sum now equals `total` exactly. If it does not, abort; this is a bug in the code, not a data problem.

Step 4's assertion is only meaningful if the residual is bounded. Without a bound, the residual absorbs *any* difference at all, so a wildly wrong `total` gets silently unloaded onto whoever owes the most instead of being caught — which is the exact class of silent failure this spec exists to prevent. The bound is 2 rupiah per participant: with four components each rounded to the nearest rupiah, one person's share can be at most 2 rupiah away from its exact value, so the total drift cannot exceed `2 * participant_count`. Anything larger means the inputs do not reconcile, and it must throw rather than reconcile itself. In practice this should never fire, because gate 1 already guarantees the receipt balances; it exists so that a caller passing inconsistent totals fails loudly.

Recomputing `amount_owed` from the rounded component values is intentional: every number visible in the UI then adds up on its own when a human checks it by hand. This is why step 2 rounds the components rather than only the final total.

### Worked example

Receipt: subtotal 71000, discount 5000, tax 6600, service 3300, total 75900. Items as in section 5.

```
Budi:
  item_subtotal  = 25000 + 15000                  = 40000
  fraction       = 40000 / 71000                  = 0.563380
  discount_share = 5000 * 0.563380                = 2816.90 -> 2817
  tax_share      = 6600 * 0.563380                = 3718.31 -> 3718
  service_share  = 3300 * 0.563380                = 1859.15 -> 1859
  amount_owed    = 40000 - 2817 + 3718 + 1859     = 42760

Sarah:
  item_subtotal  = 16000 + 15000                  = 31000
  fraction       = 31000 / 71000                  = 0.436620
  discount_share = 5000 * 0.436620                = 2183.10 -> 2183
  tax_share      = 6600 * 0.436620                = 2881.69 -> 2882
  service_share  = 3300 * 0.436620                = 1440.85 -> 1441
  amount_owed    = 31000 - 2183 + 2882 + 1441     = 33140

sum(amount_owed) = 42760 + 33140 = 75900 = total   ✓ no residual needed
```

The receipt's own maths confirms the discount base: 71000 - 5000 = 66000, and 6600 is 10% of that while 3300 is 5% of it.

## 7. Reference Code Generation

Format: `BILL_YYYYMMDD_NNN`, where YYYYMMDD is the transaction date and NNN is a zero padded sequence number that resets each day.

```
ref_code = "BILL_" + date_as_YYYYMMDD + "_" + zero_padded_sequence_number_for_that_day
```

This is plain code, no AI call involved, so it is always unique and consistently formatted.

The sequence number comes from the `bills` table: before committing, select the highest `ref_code` with that date prefix and add one. If none exist for that date, start at 001. The `unique` constraint on `ref_code` is the real guard, not this query; if two commits ever race, the second one fails the constraint and retries with a fresh number rather than silently colliding.

The date used is the transaction date from the receipt, not today. If a receipt from yesterday is logged today, its code uses yesterday's date and joins yesterday's sequence. That is correct and intentional. If `date` is null the operator must supply it in the Review and Assign screen; never silently substitute today's date, since that would misfile the bill into the wrong day's sequence and the wrong month's report.

## 8. Receipt Reading (Vision Model Prompt)

This prompt is sent from the Edge Function in section 12, along with the receipt photo.

**The authoritative copy is `supabase/functions/extract-receipt/prompt.ts`.** The block below mirrors it so this document reads as a complete specification, but when the two disagree the file wins. They have disagreed before — the schema block used to live in this prompt and stayed here long after the code dropped it — which is why the primacy is written down rather than assumed.

Note there is no schema in the prompt. The response shape is enforced by `responseSchema` at the API level (section 12), so the prompt only carries what a schema cannot express: how to read an Indonesian receipt.

```
You are extracting structured data from a photograph of an Indonesian restaurant or cafe receipt (struk).

Formatting rules for Indonesian receipts:
- Numbers use a period as the thousands separator, not a decimal point. "15.000" means fifteen thousand rupiah.
- All amounts are whole rupiah. There are no cents or decimals.
- line_total is the printed total for that line, already multiplied by quantity if the receipt shows a multiplier.
- Tax may be labeled "PPN", "Pajak", or "Pajak 11%".
- Service charge may be labeled "Service", "Svc", or "Service Charge".
- Discount may be labeled "Diskon", "Disc", or "Potongan". Report it as a positive number representing the amount subtracted.
- A rounding line may be labeled "Pembulatan". Report it exactly as printed, it can be negative.
- If a field is not printed on the receipt, use 0 for that numeric field (except subtotal and total, which should be null only if genuinely unreadable) rather than omitting the field entirely.

Accuracy rules:
- Never invent items, prices, or a place name that are not visible on the receipt.
- Receipts often print a quantity column, a unit price, and a line total on the same row, for example "2 Es Teh 8.000 16.000". Read line_total as the line total, not the unit price.
- If a printed number could be read as either a unit price or a line total, choose the reading that makes the item line totals sum to the printed subtotal.
- If any number is blurry, cut off, or ambiguous, make your best reading but note exactly what you were unsure about in confidence_notes. Do not silently guess without flagging it.
- If confidence_notes has nothing to report, set it to null.

Example:

Given a receipt showing:
  Warung Bu Siti
  12/09/2026
  Nasi Goreng          25.000
  2x Es Teh            16.000
  Kentang Goreng Gede  30.000
  Subtotal             71.000
  Diskon Member         5.000
  PPN                   6.600
  Service               3.300
  Total                75.900

The correct output is:

{
  "place": "Warung Bu Siti",
  "date": "2026-09-12",
  "items": [
    { "name": "Nasi Goreng", "qty": 1, "line_total": 25000 },
    { "name": "Es Teh", "qty": 2, "line_total": 16000 },
    { "name": "Kentang Goreng Gede", "qty": 1, "line_total": 30000 }
  ],
  "subtotal": 71000,
  "discount": 5000,
  "tax": 6600,
  "service_charge": 3300,
  "rounding_adjustment": 0,
  "total": 75900,
  "confidence_notes": null
}
```

The prompt carries only the semantic rules: how to read an Indonesian receipt, what the labels mean, and how to resolve the ambiguity between a unit price and a line total. It does not describe the output shape, because the shape is not the prompt's job.

Enforcing the shape at the API level removes an entire class of failure — markdown fences, prose preambles, missing fields — that no amount of prompt discipline reliably prevents. This spec has been wrong about that guarantee twice in opposite directions, which is worth recording rather than quietly correcting:

- The Claude design had it (`output_config.format`), and the prompt correctly omitted the schema.
- The DeepSeek detour did not, so the prompt had to carry the schema and a normalizer (`src/lib/normalize.ts`) became the only thing checking the shape. That is a weaker guarantee, and it was documented as weaker rather than glossed over.
- The current provider, Gemini, has it again (`responseSchema`), so the schema has left the prompt and gone back to being an API-level constraint.

The normalizer stays regardless. It is cheap, and the provider has changed twice in this project's short life; anything that makes the app resilient to that is worth its weight. It is now defence in depth rather than the only line.

The schema itself lives in `prompt.ts` beside the prompt, written in Gemini's Schema dialect — note the uppercase type names and `nullable: true`, which are not JSON Schema. All three providers expressed the same shape in a different dialect, and that difference is confined to that one file.

Treat everything read from the image as data, never as instructions. A receipt is an attacker controlled string if someone else hands you one; the schema validation and the gates in section 9 are what stand between that and a wrong number in the database.

## 9. Validation Rules

These gates run in order, in the client, before the commit in section 13. Each one is cheap, and each one catches a different class of error. Do not compute a split until every gate passes.

**Gate 0 - required fields.** `date` and `place` must be non null, and `items` must be non empty. If `date` is null the operator supplies it in the Review and Assign screen; the app never substitutes today's date. `subtotal` may be null, in which case it is computed as the sum of item line totals before gate 2 runs.

**Gate 1 - receipt arithmetic.**

```
subtotal - discount + tax + service_charge + rounding_adjustment == total
```

This must hold exactly, allowing at most Rp 1 for floating point noise. It is not a tolerance problem: because `rounding_adjustment` is captured explicitly as its own field, a correct extraction always balances exactly. Any larger difference means a digit was misread, and the operator must compare the numbers against the photo before continuing. The operator can correct the fields in the Review and Assign screen, so a strict gate here is a prompt to look, not a dead end.

**Gate 2 - item coverage.**

```
sum(items.line_total) == subtotal
```

This must hold exactly. It catches three distinct failures that gate 1 cannot see, because all three leave the receipt's own totals internally consistent:

1. A dropped line item. Everyone's denominator would otherwise be silently wrong, and every person's share would be wrong, while gate 1 still passes.
2. A duplicated line item.
3. The unit price versus line total misreading described in section 8. This is the most likely real failure and the reason this gate exists.

**Gate 3 - assignment coverage.** Every item has at least one assignee. Every person in the roster has at least one item. A person with no items would get a `bill_participants` row of all zeros, which is a mistake, not a legitimate outcome.

**Gate 4 - final reconciliation.** `sum(amount_owed) == total`, enforced by the residual rule in section 6. This is the gate that catches a whole category of logic bug at once, including the discount omission described in section 6. If gates 1 through 3 pass but gate 4 fails, the split code is wrong, not the receipt.

Gates 1 and 2 are the safety net between a misread digit and a wrong number recorded against someone. Gate 4 is the safety net between a coding mistake and the same outcome. The `v_bill_imbalance` view (section 4) exists so that a failure of gate 4 in production is visible rather than silent.

## 10. Receipt Photo Storage

A Supabase Storage bucket named `receipts`, **private**. No public bucket, no public URL, ever.

Object path: `{owner_id}/{ref_code}.jpg`. The reference code is already unique, so the path is unique, and the leading owner id makes the storage policies in section 12 a simple path prefix check rather than a database lookup.

Access is via short-lived signed URLs generated on demand when the operator views a receipt. The signed URL is never persisted; `bills.receipt_path` stores the path only. This is the reason the old design's "is this link public?" question does not exist here: the default is private, and a link that leaks is a link that expires.

Upload before commit, inside the same flow but not the same transaction (Storage is not transactional with Postgres). If the commit then fails, the result is an orphaned object in the bucket, which is the cheap failure. Objects are named by `ref_code`, so a retry of the same bill overwrites its own orphan rather than accumulating copies.

Photos are downscaled to about 1568 pixels on the long edge and re-encoded as JPEG before upload. iPhone captures are HEIC, which neither the vision API nor a useful web display wants, and full resolution captures are needlessly slow and expensive to send.

## 11. Review and Assign (the human step)

This is the screen where step 3 of the pipeline happens, and it is the largest single piece of user facing work in the app. It exists because the vision model is allowed to be wrong, and a human has to be the one who decides that it is right.

One screen, showing:

1. **The photo**, full size and zoomable. This is a quality control step, so the evidence and the extracted numbers have to be visible at the same time. A reviewer who cannot see the photo cannot review anything.
2. **The extracted header**: place, date, subtotal, discount, tax, service charge, rounding adjustment, total.
3. **The item list**, one row per item, with name, qty, and line total.
4. **The roster** for this bill: a list of names, addable and removable.
5. **`confidence_notes`**, surfaced prominently if non null, not buried.

Everything in 2 and 3 is **editable**. Reviewing without the ability to correct is not reviewing; a misread price that the operator has spotted but cannot fix would force them to restart the whole capture. Editing a price or a total is a first class interaction, not an escape hatch.

Assigning items: tapping an item opens a multi select of the roster. Selecting more than one name marks the item as shared and splits it evenly. Items with no assignee are visually flagged, since gate 3 blocks the commit anyway.

Recompute on every edit. The screen shows two live numbers at all times: the running per person `amount_owed`, and the sum of those against the receipt `total`. The operator watches that second number the whole time they are editing. When it reads zero, and all four gates pass, the commit action becomes available.

The commit action is disabled until gates 0 through 4 all pass, and when it is disabled it says which gate is failing. Never let the operator commit a bill whose numbers do not reconcile; that is the entire point of this screen.

## 12. Runtime and Infrastructure

**Client: an installable web app (PWA).** The development machine is Windows, and building a native iOS app requires Xcode on macOS. A PWA sidesteps that: it runs in Safari, installs to the home screen with an icon, launches without browser chrome, and needs no Mac, no App Store review, no $99 developer account, and no seven day re-signing. It is built with Vite, Svelte, and TypeScript, and deployed as static files to a free static host. The static host serves only the app bundle, holds no secrets, and does no per request work. Svelte was chosen over React for the smaller bundle and because the Review and Assign screen (section 11) is almost entirely derived state, which Svelte's reactivity expresses without the ceremony of a virtual DOM or explicit memoisation.

Capabilities this design depends on, all supported in iOS Safari today:

- Camera capture and photo library access, via two separate file inputs on `accept="image/*"`: one with `capture="environment"` for the camera, one without for the library. They cannot be the same input — `capture` removes the library option entirely rather than making it the fallback.
- Image downscaling and re-encoding in the browser before upload (section 10).
- Persistent session in `localStorage`, which survives on a home screen installed web app.

**Data access: the Supabase client, with generated types. No ORM.** This is a deliberate decision, not an omission, and it is worth recording why so it is not revisited:

- An ORM like Drizzle needs a direct Postgres connection, which means a connection string, which means the database password. That can only exist on a server. The client here is a browser, so an ORM cannot be the client's data layer even in principle.
- The entire write path is a single RPC (`commit_bill`, section 13), and most of the read path is already views (section 4). Neither is improved by a query builder.
- Type safety comes from `supabase gen types typescript --project-id <ref> --schema public > src/database.types.ts`, regenerated after every migration and committed. This is strictly better than hand maintained schema definitions, because it is generated from the database rather than being a second description of it that can drift.
- The interesting parts of this schema are the row level security policies and the `commit_bill` function. Both live in SQL migrations regardless, so SQL migrations are the source of truth either way. Adding a TypeScript schema definition on top would create a shadow copy to keep in sync for no gain.

The practical rule that follows: when a query stops being trivial, do not reach for a query builder. Put it in a view or an RPC and select from that. This is why the reporting queries are views rather than joins written in application code.

**Backend: Supabase.** Database, Storage, Auth, and one Edge Function.

**Auth.** Supabase Auth with an email and password, for a single account created once in the dashboard. The session persists in localStorage and the refresh token rotates automatically, so this is sign in once and then forget it exists.

An earlier version of this spec specified an email magic link instead, and that was wrong for this app. Three reasons, all of which only surfaced once it was actually used:

1. Supabase's built-in mailer is capped at a handful of emails per hour, and that cap cannot be raised. Iterating on anything at all exhausts it.
2. The redirect URL has to be allowlisted, and when it is not, Supabase falls back **silently** to the site URL rather than erroring. On a phone that produces a link pointing at localhost, with nothing explaining why. Failures that announce themselves are fine; this one did not.
3. The app is opened at a restaurant table with a waiter standing there. Waiting for an email to arrive is the wrong shape for that moment.

A password removes both the mailer and the redirect from the flow. Signing up is a one-time dashboard action, so the usual reason to prefer magic links — that users can self-serve — does not apply to a single-operator tool.

**Row level security.** Enabled on all four tables, denied by default:

```sql
alter table bills enable row level security;
-- ... same for the other three

create policy owner_all on bills
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy owner_all on bill_participants
  for all using (
    exists (select 1 from bills b where b.id = bill_id and b.owner_id = auth.uid())
  );

-- bill_items and bill_item_assignees follow the bill_participants pattern,
-- the latter reaching owner through its item's bill.
```

The Storage bucket needs an equivalent policy on the `receipts` bucket, matching `(storage.foldername(name))[1] = auth.uid()::text`, so the path convention in section 10 is what makes the policy work.

**The Edge Function.** One function, `extract-receipt`. It receives the downscaled image, calls the vision model with the prompt and the `responseSchema` from section 8, and returns the model's text unchanged. It deliberately does not parse, does not validate, and does not touch the database: everything that could be wrong about the model's answer is handled client side in one tested place (section 8), so a bug here can never corrupt a bill. The Gemini API key is stored as an Edge Function secret and never reaches the client.

It also refuses callers who are not signed in, and that check is load bearing rather than decorative. It is tempting to assume the platform's JWT verification covers it, but that check is satisfied by the **publishable** key — which is public by design, because it ships in the browser bundle. Without an explicit user check anyone who reads the bundle could call this function in a loop and spend the operator's API credit. No data is at risk, since the function never touches the database, but the balance is. The check reads the JWT payload rather than re-verifying a signature, which is sound here precisely because the gateway already verified it: a forged token never reaches the code, and the publishable key is not a JWT at all (no dot-separated parts), so it fails on shape before any claim is read.

This is worth the extra deploy step for three reasons. The key is not extractable from a browser bundle. There is no cross origin question to answer, which removes the largest unverified assumption from the design this replaces. And if participants ever get their own logins (section 4), the function is already the right place to put a per user rate limit.

**What this design does not have.** No Google Cloud project, no service account, no JWT assertion signing, no OAuth consent screen, no token refresh loop, no folder sharing, and no browser origin assumptions. Every one of those was a source of disproportionate complexity in the previous design.

## 13. Commit and Idempotency

The commit is one Postgres function called over RPC, so the whole bill lands in a single transaction:

```
commit_bill(bill fields, items[], participants[], assignments[])
  -> generate ref_code (section 7)
  -> insert bills row
  -> insert bill_items rows
  -> insert bill_participants rows
  -> insert bill_item_assignees rows
  -> return ref_code
```

Idempotency is handled by the database rather than by a check-then-write dance. `ref_code` is unique, so a duplicate submission fails the constraint instead of writing a second copy. The client catches that specific constraint violation and tells the operator the bill appears to already be logged.

The photo upload in section 10 happens before this call, for the reason given there. Everything else, all or nothing.

Note that a duplicate `ref_code` is the correct guard only for a genuine re-submission of the same bill. It does not stop the operator from logging two different bills on the same day, which is the common case and must keep working; the sequence number in section 7 is what makes those distinct.

## 14. Reporting

History is the database. There is no separate export path to maintain, and the app is never the system of record.

- **CSV.** A button in the app that runs a query and streams a CSV to the browser. This is roughly twenty lines and needs no dependency. The `v_monthly_spend` and `v_outstanding` views (section 4) are the two queries that matter.
- **PDF.** A `/report` route that renders the month as a clean printable page, with the browser's own Print to PDF doing the conversion. No PDF library, no server side rendering, and the output is a real document because the browser's print engine is a real print engine.

Two things worth keeping visible on the report:

1. **Outstanding per person**, from `v_outstanding`. This is the number the operator actually needs at the end of the month.
2. **Per person spend for the month**, from `v_monthly_spend` filtered to the month.

If a bill is ever edited after people have paid, note that `bill_participants` stores the computed amounts as a snapshot. Recomputing a settled bill is a deliberate action, not something that happens implicitly when an item changes.

## 15. Cost and Limits

Target is the Supabase free tier, so the running cost is zero. The limits, and what they mean at this app's scale:

- **Database: 500 MB.** A bill with six items and four participants is on the order of a kilobyte, plus the `extraction` jsonb. Even at a hundred bills a month this is years of headroom. The `extraction` column is the largest thing stored; if it ever matters, it is the obvious thing to prune.
- **Storage: 1 GB.** A downscaled receipt JPEG is roughly 300 to 500 KB, so this is on the order of two thousand receipts.
- **Egress: 5 GB per month.** One image in and out per receipt, so this is not close to a constraint.
- **Edge Function invocations: 500,000 per month.** One per receipt.

Two free tier characteristics that are not limits but will be felt:

1. **Free projects pause after seven days without activity.** A bill splitter used a few times a month will hit this. Unpausing is a click in the dashboard, and the data is intact, but it is a manual step that will happen at the worst possible moment, which is at a restaurant table. Options are to accept it, to keep the project warm with a scheduled ping, or to upgrade. Worth deciding deliberately rather than discovering.
2. **Free projects have no automated backups.** The database is a financial ledger for real money owed between friends, and "no backups" is a real exposure. Mitigation is a periodic `pg_dump` or a CSV export on a schedule the operator actually keeps. This is worth more attention than the storage limits, which are a rounding error by comparison.

## 16. Explicitly Out of Scope

1. No AI involvement anywhere except reading the receipt photo. The commit, the arithmetic, and the reference codes are plain deterministic code.
2. No multi person authentication. Participants are names, not accounts. The `user_id` seam in section 4 exists so this can change, but nothing should be built assuming it will.
3. No native iOS build in the first version.
4. No local database or offline mode in the client.
5. No automated payment status updates. Marking a bill paid is one manual toggle.
6. No AI generated reference codes.
7. No Google Sheets or Google Drive integration. This was deliberately removed; see the archived spec for that design and why it was dropped.

## Appendix: The Discount Bug, Preserved

This is the failure that an earlier draft of the split formula would have produced, kept here because it is the clearest argument for gate 4 existing.

With the split formula missing the discount term, on the worked example in section 6:

```
Budi  : 40000 + 3718 + 1859 = 45577
Sarah : 31000 + 2882 + 1441 = 35323
                      total = 80900
```

The bill was 75900. The group is overcharged by 5000, which is exactly the discount, and the discrepancy is invisible unless someone checks the sum against `total` (gate 4, section 9). Nothing in gates 1 through 3 catches it, because the receipt's own arithmetic is correct and complete.

The fix is the `discount_share` term in section 6 and the corresponding column in `bill_participants`.
